Getting started

Every request goes to this gateway's base URL, which is this host plus /api: 

https://wa-gateway-coolify.bogdanripa.com/api

Open the console, add a number, and scan the pairing QR with WhatsApp → Settings → Linked devices. The console shows a token for that number — that token is how you address it.

Then say hello:

curl -X POST $BASE/messages/text \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"to": "40750271099", "body": "Hello from wa-gateway"}'

Authentication

Send the number's token as a bearer token on every request: 

Authorization: Bearer <token>

The token selects the number. There is no channel or account id in any request — a gateway hosting five numbers gives you five tokens, and each one reaches exactly one WhatsApp account. That is also the isolation boundary: one number's token cannot see, send as, or read anything belonging to another, and it cannot reach the management API.

A missing or unknown token is 401. If a token leaks, rotate it from the console — the old one stops working immediately.

Sending

to accepts whatever you have: bare digits with the country code (40750271099), a full JID (40750271099@s.whatsapp.net), or a group id (120363012345678901@g.us).

Text

POST /messages/text
{ "to": "40750271099", "body": "Hello" }

→ { "sent": true, "message": { "id": "3EB0..." } }

Image

media is an https:// URL, a data: URI, or raw base64.

POST /messages/image
{ "to": "40750271099", "media": "https://…/cat.png", "caption": "optional" }

→ { "sent": true, "message": { "id": "3EB0..." } }

Poll

A real WhatsApp poll. Vote tallies arrive later on your webhook — see poll updates.

POST /messages/poll
{
  "to": "120363012345678901@g.us",
  "poll": {
    "name": "Lunch?",
    "options": ["Pizza", "Sushi", "Neither"],
    "allow_multiple_answers": false
  }
}

→ { "sent": true, "message": { "id": "3EB0..." }, "id": "3EB0..." }

Reaction

PUT /messages/<message-id>/reaction
{ "emoji": "👍" }        // "" removes your reaction

→ { "sent": true }

Mark as read

PUT /messages/<message-id>
{ "status": "read" }

→ { "sent": true }

Typing indicator

PUT /presences/<to>
{ "presence": "typing" }   // typing | recording | paused | available

→ { "sent": true }

Message ids in the two PUT calls are ids the gateway has seen — one it gave you from a send, or one that arrived on your webhook. They're remembered for a week.

Rate limits. Each number has an outbound cap per minute (20 by default, editable per number in the console). Exceeding it returns 502 with a message saying so, rather than queueing — it's a backstop against a loop in your bot, not a traffic shaper.

Not supported, because nothing built on this has needed them yet: documents, stickers, locations, contact cards and channels.

Groups

GET /groups/<group-id>

→ {
  "id": "120363012345678901@g.us",
  "name": "Team lunch",
  "subject": "Team lunch",
  "participants": [ { "id": "40750271099", "name": "Bogdan" }, … ],
  "participants_count": 12
}

Participant ids come back as bare digits — real phone numbers. WhatsApp is migrating identities to opaque @lid values, and the gateway resolves those back before you ever see them, so phone-prefix logic (country, language, timezone) keeps working.

Results are cached briefly, because WhatsApp rate-limits group metadata queries hard. A group the number isn't in returns 404.

Receiving

Inbound events are POSTed as JSON to the webhook URL you set for that number, with that number's token in the Authorization header so you can verify the caller.

Each request carries one of these arrays. Handle the ones you care about and ignore the rest.

messages

{
  "messages": [ {
    "id": "3EB0…",
    "from_me": false,
    "type": "text",
    "chat_id": "120363012345678901@g.us",   // or "40750271099@s.whatsapp.net"
    "chat_name": "Team lunch",
    "from": "40750271099",                   // bare digits
    "from_name": "Bogdan",
    "timestamp": 1754300000,
    "text": { "body": "Hello" }
  } ]
}

The payload carries one body field, matching type:

typefield
texttext.body
imageimage.link, image.preview, image.caption
gifgif.preview, gif.caption
voicevoice.link
audioaudio.link
link_previewlink_preview.title, .description, .preview
Media links are public and temporary. WhatsApp media arrives encrypted; the gateway downloads it, decrypts it and re-hosts it at an unguessable URL so your code — or a third party you hand the URL to, like an image or transcription model — can fetch it with a plain GET and no credentials. Links expire (48 hours by default), so fetch what you need when the event arrives.

groups

Sent when a group is joined, renamed, or its membership changes.

{ "groups": [ { "id": "…@g.us", "name": "Team lunch",
               "participants": [ { "id": "40750271099", "name": "Bogdan" } ] } ] }

contacts

{ "contacts": [ { "id": "40750271099", "name": "Bogdan" } ] }

messages_updates

Running tallies for a poll you sent. Votes are end-to-end encrypted; the gateway decrypts and aggregates them.

{
  "messages_updates": [ {
    "after_update": {
      "id": "3EB0…",                  // the poll message id
      "type": "poll",
      "chat_id": "…@g.us",
      "poll": {
        "name": "Lunch?",
        "total": 3,
        "results": [
          { "name": "Pizza",   "count": 2, "voters": ["40750271099", "40711111111"] },
          { "name": "Sushi",   "count": 1, "voters": ["40722222222"] },
          { "name": "Neither", "count": 0, "voters": [] }
        ]
      }
    }
  } ]
}
Delivery is ordered and at-least-once. Events for a number are delivered one at a time, in order — a slow endpoint delays that number's queue rather than getting events out of sequence. Non-2xx or a timeout is retried a few times, so your handler must be idempotent: dedupe on the message id.

Not forwarded at all: your own outgoing messages, status/broadcast updates, message history on reconnect, and types with no body the API models — stickers, documents, locations, contact cards and non-GIF video.

Status

GET /health   → 200 always while the service is running
{ "ok": true, "connected": 2, "total": 3 }

GET /ready    → 200 only when every number is connected, else 503
{ "ok": false, "connected": 2, "total": 3,
  "sessions": [ { "id": "gepetel", "status": "connected" },
                { "id": "second-bot", "status": "awaiting-pairing" } ] }

Both are public and deliberately carry no credentials. /health answers "is the process alive"; /ready answers "can every number actually send", which is the one to alert on — a number that quietly needs re-pairing shows up here.

Managing numbers

Everything the console does is an HTTP call, if you'd rather script it. These need the management key, not a number's token: 

Authorization: Bearer <management key>
GET /mgmt/numbersevery number: status, pairing QR, token
POST /mgmt/numbers{ id, webhookUrl, pairPhone?, sendRatePerMinute? } → its new token
PATCH /mgmt/numbers/:idchange webhook URL, pairing phone or rate cap
POST /mgmt/numbers/:id/rotate-tokenissue a new token, revoking the old one
POST /mgmt/numbers/:id/relinkunlink from WhatsApp and show a fresh QR
POST /mgmt/numbers/:id/restartreconnect without touching credentials
DELETE /mgmt/numbers/:idremove the number and purge its stored state

The management key can add numbers and read every token, so treat it as the most sensitive credential here. Repeated bad guesses from one address are locked out.
