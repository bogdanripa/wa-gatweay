Getting started

Every request goes to this gateway's base URL, which is this host plus /api: 

https://wa-gateway.example.com/api

Open the console, add a number, and scan the pairing QR with WhatsApp → Settings → Linked devices. The console shows a token for that number — that token is how you address it.

Coming from the WhatsApp Business Cloud API? Change your base URL to the one above and stop. The request bodies, the response envelope and the webhook payloads are Meta's — your existing code keeps working. See differences from Meta for the short list of what is not the same, all of which is this gateway being less restricted.

Then say hello — this is Meta's exact request:

curl -X POST $BASE/$PHONE_NUMBER_ID/messages \
  -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "messaging_product": "whatsapp",
    "recipient_type": "individual",
    "to": "12025550100",
    "type": "text",
    "text": { "body": "Hello from wa-gateway" }
  }'
→ {
  "messaging_product": "whatsapp",
  "contacts": [ { "input": "12025550100", "wa_id": "12025550100" } ],
  "messages": [ { "id": "3EB0..." } ]
}

$PHONE_NUMBER_ID is shown on the number's card in the console. The path segment is accepted but not used for routing — the token already identifies exactly one number — so an existing Cloud API URL works verbatim, and so does the number's own id. What it will not do is let one number's token send from another's.

Authentication

Send the number's token as a bearer token on every request: 

Authorization: Bearer <token>

The token selects the number. There is no channel or account id in any request — a gateway hosting five numbers gives you five tokens, and each one reaches exactly one WhatsApp account. That is also the isolation boundary: one number's token cannot see, send as, or read anything belonging to another, and it cannot reach the management API.

A missing or unknown token is 401. If a token leaks, rotate it from the console — the old one stops working immediately.

Sending

Every message is a POST to /<PHONE_NUMBER_ID>/messages with messaging_product: "whatsapp" and a type, exactly as Meta specifies. to takes a phone number with country code, or a group id with recipient_type: "group".

Text

{ "messaging_product": "whatsapp", "recipient_type": "individual",
  "to": "12025550100", "type": "text",
  "text": { "preview_url": false, "body": "Hello" } }

To a group

{ "messaging_product": "whatsapp", "recipient_type": "group",
  "to": "120363000000000000@g.us", "type": "text",
  "text": { "body": "Hello everyone" } }

Any group the linked number belongs to. Meta's Groups API only addresses groups the business itself created — see differences.

Media

link takes an https URL, a data: URI, or raw base64.

{ … "type": "image",    "image":    { "link": "https://…/cat.png", "caption": "optional" } }
{ … "type": "video",    "video":    { "link": "https://…/clip.mp4", "caption": "optional" } }
{ … "type": "audio",    "audio":    { "link": "https://…/note.ogg" } }
{ … "type": "sticker",  "sticker":  { "link": "https://…/s.webp" } }
{ … "type": "document", "document": { "link": "https://…/f.pdf", "filename": "f.pdf" } }

Location

{ … "type": "location",
  "location": { "latitude": 51.5000, "longitude": -0.1200,
                "name": "Example Place", "address": "1 Example Street" } }

Poll

An extension — Meta has no poll type. The Cloud API cannot send a poll at all, so there is no official shape to match and this one is ours. It follows Meta's conventions exactly — a top-level object named after the type, snake_case fields — so it reads like the rest of the API, and selectable_count is WhatsApp's own wire field (selectableOptionsCount) rather than an invention. Votes come back as inbound poll_response messages, each carrying the full running tally. 
POST /<PHONE_NUMBER_ID>/messages
{ "messaging_product": "whatsapp",
  "recipient_type": "group",
  "to": "120363000000000000@g.us",
  "type": "poll",
  "poll": {
    "name": "Lunch?",
    "options": ["Pizza", "Sushi", "Neither"],
    "selectable_count": 1
  } }
field
nameThe question. Required.
optionsTwo or more answers. Blank entries are dropped before that check.
selectable_countHow many options one person may pick. 1 is a single-answer poll; the option count lets anyone pick all of them; anything between is a real limit — "choose up to 2 of 5" is just 2. Defaults to 1.
allow_multiple_answersAccepted as a convenience if you have a boolean to hand: true means the option count. Ignored when selectable_count is given.

Note it is not the inverted "0 means unlimited" convention some APIs use — 0 is indistinguishable from unset and reads as a bug at every call site.

Reaction

{ … "type": "reaction",
  "reaction": { "message_id": "3EB0…", "emoji": "👍" } }   // "" removes it

Mark as read, and typing

A status update, not a message — so it carries no to, same as Meta.

{ "messaging_product": "whatsapp", "status": "read", "message_id": "3EB0…" }

// with a typing indicator, as Meta models it
{ "messaging_product": "whatsapp", "status": "read", "message_id": "3EB0…",
  "typing_indicator": { "type": "text" } }

Errors

Meta's error envelope, so existing error handling keeps matching:

{ "error": { "message": "(#100) Missing or invalid parameter: text.body",
             "type": "OAuthException", "code": 100,
             "error_data": { "details": "text.body must be a non-empty string." } } }
Rate limits. A number can carry an outbound cap per minute, set per number in the console. There is no default — leave it empty and the number is uncapped. Where a cap exists, exceeding it returns 502 rather than queueing: it's a backstop against a loop in your bot, not a traffic shaper.

Not supported: template (there is no 24-hour window here to need one), interactive, and contacts messages.

Groups

GET /groups/<group-id>

→ {
  "id": "120363000000000000@g.us",
  "name": "Team lunch",
  "subject": "Team lunch",
  "participants": [ { "id": "12025550100", "name": "Alex Doe" }, … ],
  "participants_count": 12
}

Participant ids come back as bare digits — real phone numbers. WhatsApp is migrating identities to opaque @lid values, and the gateway resolves those back before you ever see them, so phone-prefix logic (country, language, timezone) keeps working.

Results are cached briefly, because WhatsApp rate-limits group metadata queries hard. A group the number isn't in returns 404.

Receiving

Inbound events are POSTed as JSON to the webhook URL you set for that number, with that number's token in an X-Wa-Gateway-Token header so you can verify the caller.

Not the Authorization header. A webhook URL often points at something that owns that header for its own authentication — ntfy.sh, for one, reads it and returns 401 for any credential it doesn't recognise, which fails every delivery. The token goes in X-Wa-Gateway-Token, which nobody else claims.

The webhook is optional, so you can pair a number before its bot exists. Until one is set, inbound events are discarded, not queued — otherwise a number left paired for a week would flood its bot with stale conversation the moment a URL appeared. Sending works throughout.

An incoming message

Meta's envelope, nesting and field names, unchanged:

{
  "object": "whatsapp_business_account",
  "entry": [ {
    "id": "<BUSINESS_ACCOUNT_ID>",
    "changes": [ {
      "field": "messages",
      "value": {
        "messaging_product": "whatsapp",
        "metadata": {
          "display_phone_number": "12025550199",
          "phone_number_id": "<PHONE_NUMBER_ID>"
        },
        "contacts": [ { "profile": { "name": "Alex Doe" }, "wa_id": "12025550100" } ],
        "messages": [ {
          "from": "12025550100",
          "id": "3EB0…",
          "timestamp": "1754300000",
          "type": "text",
          "text": { "body": "Hello" }
        } ]
      }
    } ]
  } ]
}

timestamp is a string of seconds, as Meta sends it.

From a group

Identical, with a group_id on the message and the participant's number in from — exactly how Meta represents a group message: 

"messages": [ {
  "from": "12025550100",              // who sent it
  "group_id": "120363000000000000@g.us",
  "id": "3EB0…", "timestamp": "1754300000",
  "type": "text", "text": { "body": "Hello everyone" }
} ]

Replies

A message that replies to another carries a context object, in Meta's shape. It is present only on replies — a message that quotes nothing has no context key at all, so existing handling is unaffected. 

"messages": [ {
  "from": "12025550100",
  "id": "3EB0…",
  "timestamp": "1754300000",
  "context": {
    "id":   "3EB0AAAA…",      // the message being replied to
    "from": "12025550199"     // who sent that message
  },
  "type": "text",
  "text": { "body": "yes, agreed" }
} ]

On every message type, not just text — a reply to a photo or a voice note carries it too. context.from is the quoted sender as bare digits, resolved from a LID like any other id. When the quoted message is one you sent, that is an ordinary reply and context.from is your own number, which is how a bot can tell someone replied to it.

Message types

texttext.body
imageimage.link, .caption, .mime_type
videovideo.link, .caption — GIFs arrive as video, as they do on WhatsApp

Media links are public and temporary. Meta gives you a media id to exchange for a URL; this gateway has already downloaded and decrypted the file and gives you link directly — a plain GET, no credentials, so you can hand it to an image or transcription model as-is. Links expire (48 hours by default), so fetch what you need when the event arrives.

Poll votes

An extension — Meta has no polls in either direction. The Cloud API can neither send nor receive them, so there is no official shape. This follows how Meta models button_reply and list_reply: the response is an ordinary inbound message of type interactive whose context points at what it responds to — the same context object a reply carries. 
"messages": [ {
  "from": "12025550100",              // who voted
  "id": "<id of this vote event>",
  "timestamp": "1755870000",
  "type": "interactive",
  "context": {
    "from": "12025550199",            // who sent the poll — your number
    "id": "<id of the POLL message>"  // ← join on this
  },
  "interactive": {
    "type": "poll_response",
    "poll_response": {
      "selected_options": [ { "id": "0", "title": "Pizza" } ],
      "results": [
        { "id": "0", "title": "Pizza",   "count": 3, "voters": ["12025550100", "12025550142"] },
        { "id": "1", "title": "Sushi",   "count": 1, "voters": ["12025550177"] },
        { "id": "2", "title": "Neither", "count": 0, "voters": [] }
      ],
      "total": 4
    }
  }
} ]
field
context.idThe id of the poll message you sent — the same id returned in messages[0].id when you posted it. This is what joins a vote to its poll.
selected_optionsThis voter's complete current choice, not a delta. Several entries for a multi-select poll; an empty array when they clear their vote.
resultsThe full tally for every option, including ones nobody picked. id is the option's index, stable for the life of the poll, so key on it rather than the title.
totalSum of all counts.

A delivery arrives on every change — a new vote, a changed vote, a cleared one. Because each carries the whole tally rather than an increment, a missed or out-of-order delivery corrects itself on the next one, and nothing downstream has to accumulate counts of its own.

Delivery is ordered and at-least-once. Events for a number are delivered one at a time, in order — a slow endpoint delays that number's queue rather than reordering it. Non-2xx or a timeout is retried, so your handler must be idempotent: dedupe on the message id.

Not forwarded: your own outgoing messages, status/broadcast updates, history on reconnect, and types with no payload here — stickers, documents, locations and contact cards inbound.

Status

GET /health   → 200 always while the service is running
{ "ok": true, "connected": 2, "total": 3 }

GET /ready    → 200 only when every number is connected, else 503
{ "ok": false, "connected": 2, "total": 3,
  "sessions": [ { "id": "my-bot", "status": "connected" },
                { "id": "second-bot", "status": "awaiting-pairing" } ] }

Both are public and deliberately carry no credentials. /health answers "is the process alive"; /ready answers "can every number actually send", which is the one to alert on — a number that quietly needs re-pairing shows up here.

Managing numbers

Everything the console does is an HTTP call, if you'd rather script it. These need the management key, not a number's token: 

Authorization: Bearer <management key>
GET /mgmt/numbersevery number: status, pairing QR, token
POST /mgmt/numbers{ id, webhookUrl, pairPhone?, sendRatePerMinute? } → its new token
PATCH /mgmt/numbers/:idchange webhook URL, pairing phone or rate cap
POST /mgmt/numbers/:id/rotate-tokenissue a new token, revoking the old one
POST /mgmt/numbers/:id/relinkunlink from WhatsApp and show a fresh QR
POST /mgmt/numbers/:id/restartreconnect without touching credentials
DELETE /mgmt/numbers/:idremove the number and purge its stored state

The management key can add numbers and read every token, so treat it as the most sensitive credential here. Repeated bad guesses from one address are locked out.

Differences from Meta

The shapes above are Meta's. The behaviour behind them is not identical, and every difference below is this gateway being less restricted — because it is a linked device on a real WhatsApp account rather than a Business Platform tenant.

WhatsApp Cloud APIwa-gateway
Opening a conversation Approved template required outside the 24-hour service window No window and no templates — send text whenever
Which groups Only ones created through the Groups API, with the business as admin Any group the linked number is in
Group ids Opaque tokens minted by the Groups API (Y2FwaV9ncm91cDo…) WhatsApp's own group ids (1203…@g.us)
Group creation, invite links, join approval Dedicated endpoints Not supported — create and join on the phone
Polls No poll type — cannot send one type: "poll", with tallies on a webhook
Media A media id you exchange for a URL A public, temporary link, already decrypted
Onboarding Business verification, an app, a WABA Scan a QR
Cost Per conversation Your electricity bill
Delivery/read receipts outbound statuses[] webhooks Not emitted
interactive, template, contacts messages Supported Rejected with a (#100) error naming the type

And the obvious one: this drives WhatsApp through an unofficial client, so it has no SLA and no support contract. Meta's platform is the right choice for anything where those matter.
